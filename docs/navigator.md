# FDML Navigator — слой индекса: что это, скоуп, продукты, метрики

Статус: рабочая концепция тулсета. Это **не** часть спеки FDML — спека не меняется.
Это расширение инструментария: `fdml index / search / outline / flow / mark / facts`
и то, что из них вырастает.

---

## 1. Имя и место в системе

Рабочее имя слоя — **Navigator** (команды остаются как есть: `fdml index`, `fdml search`…).

Это НЕ та же задача, которую решает ядро FDML, и это важно разделить:

| | Ядро FDML (scan → graph → flows → assemble) | Navigator (index / search / outline / flow) |
|---|---|---|
| Продукт | **спека** — бизнес-читаемая модель (entities, actions, features, flows) | **рабочая память кодовой базы** — где что лежит и что читать |
| Вопрос | «*зачем* этот код существует, *что* он реализует» | «*где* это, *что* его вызывает, *какие 40 строк* читать» |
| Потребитель | человек-владелец продукта, viewer, vision.fdml | агент и разработчик в рабочем цикле, прямо сейчас |
| Темп | артефакт, живёт в git, обновляется осознанно | одноразовый, `.fdml/index.sqlite`, перестраивается за секунды |

Общее у них — детерминированные экстракторы (tree-sitter) и call-графы. Navigator —
это **сенсорный слой**: он щупает код и рабочие запросы. Ядро — **модельный слой**.
Сенсор кормит модель (те же сканеры, `code_ref`-мосты), но продукты разные.

Восстановление структуры классов/объектов/флоу/сущностей — да, Navigator это делает,
но как *побочный продукт навигации*, без бизнес-интерпретации. Интерпретация
(«это фича, она реализует подписку») — работа ядра и vision-слоя.

## 2. Два продукта, которые рождаются из индекса

### 2.1 Health — гардеры и здоровье кодовой базы

Индекс уже знает достаточно, чтобы judgить код, а не только искать по нему:

- **god-функции** — `⚠ god function: 6527 lines` уже печатается в выдаче поиска.
  Это первый гардер. Замер: 48.3% чтений агента приземляются внутрь таких тел —
  каждая god-функция — это налог на каждый будущий запрос;
- кандидаты в мёртвый код — символы без вызывающих (call-граф есть);
- перекос файлов, шум генерированного кода, плотность комментариев на границах фаз
  (метки `outline` бесплатны только там, где код комментирован — само отсутствие
  меток есть сигнал);
- стабильность API — прототип vs определение, расползание дублей имён.

Форма: `fdml health` — отчёт с severity, позже — линты в CI тем же ratchet-механизмом,
что описан для value-графа. Это задачи рефакторинга, «выданные» индексом.

### 2.1b Кампании оптимизации — глубокая аналитика поверх Health

Health находит проблемы; **кампания** упаковывает их в план работ с посчитанной
окупаемостью. Глобальная цель одна: привести кодовую базу к читаемому виду и
**удешевить работу LLM с ней** — и это не вкусовщина, а измеренная экономика:

- меньше кода в контексте: `get` на god-функции = 98 853 токена, `outline` = 11 КБ
  (×36) — каждый нераспиленный монолит оплачивается токенами при каждом заходе;
- точечные правки: якорь/маленькая функция = правка в окне ~40 строк; 48.3% чтений
  агента сейчас падают внутрь тел, которые нечем адресовать;
- меньше ретраев: 63% поисковых усилий — повторные попытки; понятные имена и
  границы бьют прямо в М1.

**Три типа кампаний** (по возрастанию риска, у каждой — детальный план «что и зачем»):

| Тип | Что делает | Риск | Примеры пунктов плана |
|---|---|---|---|
| **Экономичная** | приведение к общему виду без семантических изменений: тулинг, форматирование, комментарии на границах фаз, имена-переименования, изгнание шума из индекса | ~нулевой | «46 фаз `main()` без меток — добавить комментарии-заголовки: метки outline станут бесплатными»; «включить форматтер»; «вынести генерированные файлы из скана» |
| **Оптимальная** | код переписывается точечно: распил god-функций по уже вычисленным якорям, удаление мёртвого кода (сироты call-графа), дедупликация | средний, под тестами | «`main()` 6527 строк → 20 функций по границам фаз (границы уже посчитаны outline)»; «удалить N символов без вызывающих» |
| **Агрессивная** | переделка архитектуры: границы модулей, разрыв циклов, выделение слоёв | высокий | «вынести режимы-аудиты из `main.c` в отдельные команды»; «разорвать цикл A↔B» |

**Приоритизация — синтез с Routinizer, и это ключ:** чинить не то, что некрасиво,
а то, обо что агенты реально спотыкаются. Приоритет пункта =
`горячесть (частота запросов/чтений из лога) × нездоровье (Health-метрика)`.
Пример из замера: `main.c` собрал 23% всей активности сессии И является худшей
god-функцией — он и есть пункт №1 любой кампании по OpenUG2. Холодный уродливый
файл может ждать вечно.

**Каждый пункт плана обязан нести:** что делаем → какой измеренный сигнал это
оправдывает → ожидаемый эффект на М1/Health-метрики → риск и способ проверки
(тесты/поведение). После кампании — тот же индекс перемеряет метрики: до/после.
Кампания без дельты метрик — не выполнена, а нарисована.

Кампания — это **план-досье**, а не автоматическая правка: генерирует его Navigator,
исполняет агент отдельно, пункт за пунктом, с ratchet'ом как в CI-линтах.

### 2.2 Routinizer — рутинизация повторяющихся задач агента

Ключевая идея слоя. Индекс стоит между агентом и кодом, значит он **видит все
запросы**. Замер показал: 63.1% поисковых усилий агента — ретраи, одни и те же
понятия ищутся по 5–7 раз за сессию, одни и те же цепочки восстанавливаются грепом
заново. Каждый повтор — кандидат в рутину.

Механика:
1. Navigator **логирует запросы** (локально, в тот же sqlite: запрос, результаты,
   был ли полезен — см. метрику №2, что агент сделал после);
2. из лога извлекаются паттерны: «этот концепт ищут постоянно» → `fdml mark`
   автоматом-кандидатом; «эту цепочку восстанавливают руками» → готовый `--flow`;
   «этот тип задачи повторяется» → **тулкит/скилл**, сгенерированный по данным;
3. харнесс `research/nav-bench/harness.py` — прототип этого экстрактора: он уже
   умеет доставать пары «запрос → куда пришёл» из транскриптов.

То есть Navigator — **первый рутинизатор для любой кодовой базы**: не мы придумываем,
какие тулзы нужны агенту, — лог запросов сам говорит, что рутинизировать следующим.
Всё, что делалось до этого, не решало реальных задач, потому что строилось от
предположений; этот слой строится от наблюдаемого поведения.

### 2.3 Продуктовый вектор — мост между Navigator и бизнес-слоем FDML

Связь нового флоу со старым (vision.fdml, feature map, value-граф 1.4.1). Три
источника фактов уже существуют:

1. **индекс** — что в коде есть сейчас;
2. **история сессий Claude** — что пользователь и агент реально делали: запросы,
   правки, последовательности действий (харнесс уже умеет это доставать);
3. **git-история** — что менялось и когда; где коммит-месседжи не объясняют —
   дообъясняет LLM по диффам.

Пайплайн (оффлайн-аналитика — здесь эмбеддинги/LLM уместны, это не горячий путь):

```
сессии + git ──> классификация эпизодов по интентам ──> таймлайн «что делали и зачем»
                 (чинил баг / строил фичу /                        │
                  рефакторил / ресерчил)                           ▼
индекс ─────────────────────────────────────────────>  ПРОДУКТОВЫЙ ВЕКТОР
                                                       (куда продукт реально движется,
                                                        выведено из фактов, не из слов)
```

**Что это даёт карте фичей — новый статус.** Раньше value-граф заполнялся руками
и был заявкой; теперь у него есть измеренная подложка, и карта фичей становится
**стартовой точкой для агента-CPO** с двумя задачами:

- **оценка value фичей по фактам**: фичу постоянно чинят → кандидат в `degraded`;
  код фичи никто не трогал и не запрашивал → кандидат на выпил; фича горячая в
  запросах и растёт в коммитах → ядро продукта. Это заполнение `status` и
  приоритетов value-графа данными вместо мнений;
- **предложения «что добавить и зачем»**: повторяющиеся ресерчи без последующей
  фичи = неудовлетворённая потребность; разрыв между вектором и vision = либо
  дрейф, либо недостающая фича. Gap-отчёт становится направленным.

Итого рекурсия замыкается полностью: Navigator наблюдает работу → вектор объясняет
«что делали и зачем» → карта фичей получает факты → агент-CPO предлагает следующий
шаг → его исполнение снова наблюдает Navigator.

### 2.4 Вечное улучшение тулинга — самонастройка под конкретный проект

Флоу простой, и он уже работает:

```
вызов тулы ──> success? ──да──> ок (записано)
                  │
                  нет ──> агент идёт в grep (сам или через наш --llm фолбек)
                  │
                  └──> МЫ ЭТО ВИДИМ КАК ФЕЙЛ ──> кейс копится в query_log
                                                       │
                             fdml log  <───────────────┘
                       (хит-рейт + накопленные кейсы этого проекта)
```

Реализовано сегодня: каждый `fdml search` пишет в `query_log` (запрос, top score,
useful, сработал ли LLM-фолбек и спас ли); `fdml log` показывает хит-рейт, фейлы,
статистику фолбека и **ретрай-эпизоды**. Фейл — не шум, а **кейс**: указание, чему
тул должен научиться именно в этом проекте.

Принципиально: **фидбека от агента не требуется** — никакой лишней работы ему.
Все сигналы пассивные, видны из самого вызова: вердикт — score-порог; уход в LLM —
флаги `llm_used`/`llm_rescued`; а самый сильный сигнал — **цепочка переформулировок**
(несколько фейлов подряд в пределах 90 секунд): агент, не найдя, ищет другими
словами — лог видит это сам, агент даже не знает, что пожаловался.

Как кейс превращается в улучшение — меню рычагов, по возрастанию цены:

| Рычаг | Когда |
|---|---|
| `fdml mark "<запрос>" <место>` | концепт без лексического пересечения — самое частое |
| стоп-слова / скоупинг | шумный или неоднозначный запрос (монорепо) |
| порог / веса ранжирования | правильный ответ есть, но не в топ-3 |
| новая экстракция (вид литерала, поле якоря) | класс данных не индексируется |
| **кандидат в новый тул** | кейс не закрывается ничем выше — сигнал Routinizer'у |

Периодический проход (агент или человек) разбирает `fdml log`, выбирает рычаг на
кейс, перепрогоняет запрос — кейс закрыт. Закрытые кейсы = регрессионный набор
тула для этого проекта (харнесс умеет их реплеить). Так тул **дотягивается под
проект данными его же использования** — идеала не нужно, нужен работающий цикл.

Тот же паттерн позже применим к остальным слоям (facts, flows, outline — каждый
пишет свой сигнал успеха), но начинаем только с search: один слой, живой цикл.

## 3. Две базовые метрики слоя

**М1 — сокращение времени ресёрча задачи агентом.** База базовая. Измеряется по
транскриптам: число grep/read-ходов и прочитанных токенов до первой правки, доля
ретраев. Бейзлайн уже снят: 2.71 грепа на эпизод, 36% эпизодов ≥3 попыток,
`get` на god-функции = 98 853 токена против 11 КБ у `outline`. Каждый релиз слоя
обязан двигать эту метрику, иначе это украшательство.

**М2 — честный отрицательный результат.** Если полезного ответа нет, инструмент
обязан сказать «тут пусто, не сработало», а не отдавать мусор с score 0.14.
Конкретно:
- в JSON — поле `useful: false` + причина (нет совпадений / всё ниже порога /
  неоднозначно: N равных кандидатов);
- в тексте — явная строка «no useful result, fall back to grep»;
- каждый такой случай **логируется** — это сырьё Routinizer'а (провал запроса =
  самый ценный сигнал: чего слою не хватает).
Позже это оборачивается в скилл: агент получает инструкцию «спроси Navigator;
если он сказал „пусто" — грепай, а провал уже записан».

## 4. Принцип адаптеров: не писать языковые слои самим. Никогда

Урок оплачен замером: рукописный C-сканер (42 строки) давал **40% recall**;
готовая грамматика tree-sitter — **99.8%**. Правило:

> Для любого языка/анализа сначала ищется существующий парсер/движок. Если он есть —
> он скачивается в `adapters/` (или подключается крейтом-грамматикой), сколько бы ни
> весил, и закрывает нашу задачу через файловый контракт. Свой парсер пишется только
> если готового нет вообще.

Действующие точки расширения:
- **грамматики** — tree-sitter-крейты (C, Rust, Python, Java, C#, JS, TS, Go — уже);
- **факты** — `fdml facts --import` (Frama-C Eva работает, Joern — по потребности),
  схема в `docs/facts-provider.md`; флоу тоже провайдер-дополняемы (`augmented_by`);
- то же для будущих: LSP-выжимки, coverage, git-churn — всё через файлы фактов.

### 4.1 Статус готовности языковых бекендов (добить)

| Слой | C | Rust | Python | Java | C# | JS | TS | Go |
|---|---|---|---|---|---|---|---|---|
| символы → `search` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| call-рёбра → `flow`/`impact`/`outline` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `mark`/`facts`/`log`/`--llm` (языконезависимы) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| якоря в god-функциях | ✅ | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |
| литералы (флаги/форматы/ассеты) | ✅ | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |
| recall замерен против ctags | ✅ 99.8% | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |

Долг по каждому «❌» в двух нижних строках: экстрактор навигационного слоя —
~100 строк по готовому шаблону (`navigation_layer` в `src/scanner/c.rs`,
`rust_lang.rs`), меняются только имена узлов грамматики. Замер recall — прогон
ctags-сравнения из `research/nav-bench/` по одному реальному репо на язык;
правило «не мерили ≠ хорошо» оплачено на C (рукописный сканер давал 40%).

Порядок добивания — по `fdml log`, не по алфавиту: первыми TS и Python (реально
используются в замеренных репах), остальные — когда появятся кейсы.

## 5. Судьба god-функций — что мы видим и чего нет

Частый вопрос: «объявления полей не индексируем — как тогда восстанавливаем флоу?»
Разделение такое:

**Видим (и этого достаточно для флоу):**
- call-рёбра с номерами строк — внутри 6527-строчной `main()` их 2225; флоу и
  `outline` строятся на них, локальные переменные для этого не нужны;
- топ-левел блоки как якоря (условие, вызовы, комментарий, литералы);
- **инициализированные** локальные (`const int COUNTDOWN = 180`) — как признаки
  якоря, находимые поиском, но не отдельные символы;
- литералы с ролью (флаг CLI, формат лога, ассет) — привязаны к якорю.

**Не видим намеренно:** голые объявления (`int i`, `char *tmp`) — 1118 штук в одной
`main()`, они удвоили бы индекс шумом и сломали ранжирование.

**Не видим и не будем видеть своим парсером:** поток данных через переменные
(«какая переменная несёт состояние между фазами»). Это задача value/data-flow
движков — Eva и Joern через адаптеры фактов, по требованию, вне горячего пути.

Итого god-функция для Navigator: сигнал `⚠` в поиске + разрез `outline` на фазы +
якоря для точного попадания. Для Health она — топ-находка на рефакторинг.

## 6. CLI для человека (предложения, по убыванию ценности)

1. `fdml flow "<запрос>"` — то, что сейчас `search --flow`, но как самостоятельный
   ответ: найти лучший символ и показать дерево цепочек entry → … → symbol → next,
   с `file:line` на каждом хопе. «Сделал запрос — увидел полный флоу».
2. `fdml health` — отчёт §2.1: god-функции, сироты, шум, дубли, размерные перекосы.
3. `fdml map` — терминальная карта проекта: модули, размеры, число символов,
   флаги здоровья; вид «куда я попал» за 2 секунды в незнакомой репе.
4. `fdml why <file:line>` — обратный запрос: чья это строка (функция → якорь →
   фаза → кто вызывает) — контекст места одним вызовом.
5. `fdml log` — последние запросы и провалы (окно в Routinizer).

## 7. Визуал (осознанно последним): вкладка Index в serve

Идеал: `fdml serve` → вкладка **Tooling**, внутри неё Navigator: карта индекса +
`fdml log` (кейсы улучшения тулинга, §2.4) рядом. Кнопка «построить». Индексация стримится
в страницу (у serve уже есть SSE-каналы и generation-status — переиспользовать),
и карта проявляется «как звёзды»: файлы-узлы по мере парсинга, рёбра вызовов,
метрики счётчиками, god-функции красным, якоря при зуме внутрь файла, метки и
факты движков поверх. Файл-вотчер serve уже есть — карта живёт в реальном времени
при правках. Заметки — это `fdml mark` прямо с карты.

Порядок сборки, когда дойдём: (1) кнопка+прогресс на существующем SSE,
(2) статичная карта из готового sqlite (данные уже все есть: files/symbols/
references/anchors), (3) live-обновление, (4) зум в файл и метки. Не раньше, чем
М1/М2 заработают в CLI — карта продаёт слой, но метрики его оправдывают.

## 8. Что уже есть vs что дальше

Есть сегодня: индекс 9-й версии (символы 99.8% recall, якоря, литералы, метки,
факты, флоу), 4 языка проверены бенчем (`research/nav-bench/RESULTS.md`),
скорость — секунды на индекс, миллисекунды на запрос.

Очередь (по метрикам, не по красоте):
1. ✅ М2 — сигнал «no useful result» + `query_log` + `fdml log` (сделано);
2. скоупинг для монореп (измеренная слабость: `corev2` × 5 сервисов);
3. `fdml flow` / `health` / `why` из §6;
4. Routinizer-экстрактор поверх лога (эволюция harness.py);
5. `fdml campaign --type экономичная|оптимальная|агрессивная` — генерация
   плана-досье из Health × лога запросов (§2.1b); требует пп. 1 и 4;
6. вкладка Index в serve;
7. продуктовый вектор (§2.3): классификатор интентов по сессиям+git → факты в
   value-граф → агент-CPO. Требует лога запросов (п.1) и Routinizer (п.4).

Экспериментально уже есть: `fdml search --llm` — фолбек на локальную LLM, когда
детерминированный слой честно сказал «пусто» (М2-гейт: top score < 0.55). Модель
выбирает из пронумерованных греп-улик с привязкой к символам — выдумать путь не
может, провенанс `llm-fallback` виден в выдаче. Замер на mined-бенче OpenUG2:
file@3 51% → 55%, цена ~8.5 с на сработавший запрос (12 из 52), в остальных 40
запросах LLM не вызывается вовсе.
